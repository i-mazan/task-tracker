# Настройка Supabase для TaskFlow

## 1. Проект и авторизация

1. Создай проект в https://supabase.com/dashboard. Дождись готовности БД.
2. В Authentication → Sign In / Providers включи Email / Password.
3. В настройках Auth отключи **Allow new users to sign up**. Пользователи создаются администратором через Dashboard.
4. В Authentication → URL Configuration укажи **Site URL**:
   `https://i-mazan.github.io/task-tracker/`
   Если используешь другой адрес или custom domain, подставь фактический URL.
5. В **Redirect URLs** добавь этот же URL и для локальной проверки:
   `http://localhost:8000/`
   Используй адрес с завершающим `/`, как при открытии приложения.
6. В Authentication → Users → Add user → Create new user задай email и пароль. Для аккаунта, созданного вручную, включи Auto Confirm User, если эта опция предлагается.

## 2. Таблицы, RLS и Realtime

1. Открой SQL Editor → New query.
2. Скопируй **весь** файл `supabase/schema.sql`, нажми Run. Это первоначальная миграция, её выполняют один раз в новом проекте.
3. Проверь появление `taskflow_items` и `taskflow_operations` в Table Editor.
4. Таблицы имеют RLS. Клиент может читать только свои элементы. Запись выполняется через `taskflow_apply`, которая сама определяет владельца из сессии, проверяет версии и сохраняет подтверждения операций.
5. SQL уже добавляет `taskflow_items` в publication `supabase_realtime`. Проверь это в настройках Publications / Replication. `taskflow_operations` включать в Realtime не нужно.

Задачи и идеи хранятся отдельными строками одной таблицы, поле `kind` различает `tasks` и `ideas`. Удалённые строки сохраняются с `deleted=true`, чтобы отключённое устройство не воскресило старые данные. Не удаляй tombstones и подтверждения операций вручную: они нужны для безопасной синхронизации старой очереди. Подтверждения удаляются автоматически только после надёжного сохранения результата клиентом.

### Обновление существующего проекта: очистка подтверждений

Если первоначальный `schema.sql` уже выполнен, запусти в SQL Editor только `supabase/002_receipt_cleanup.sql`. Для нового проекта функция очистки уже включена в `schema.sql`.

После успешной отправки клиент атомарно сохраняет результат, удаляет операцию из очереди изменений и добавляет её ID в локальную очередь очистки. Функция `taskflow_acknowledge` удаляет только подтверждения текущего пользователя; повторный вызов безопасен. Ошибки очистки не блокируют отправку задач, ID остаются для повторной попытки. После выхода незавершённая очистка продолжится при следующем входе в тот же аккаунт.

Подтверждения, обработанные старой версией приложения, автоматически не удаляются: у неё не было очереди очистки. Эта миграция предотвращает дальнейшее накопление для новой версии. Старые записи требуют отдельного решения о безопасном сроке хранения.

## 3. Подключение приложения

1. Project URL этого проекта: `https://ofvezvetogqenxbrqbfc.supabase.co`. Его также можно найти в Connect.
2. В Settings → API Keys скопируй **Publishable key** (`sb_publishable_...`). Старый `anon` key также поддерживается.
3. `supabase-config.js` уже заполнен для текущего проекта. Для другого проекта замени значения:

```js
window.TASKFLOW_CONFIG = {
  url: 'https://YOUR_PROJECT.supabase.co',
  publishableKey: 'sb_publishable_...',
};
```

Эти значения публичные и могут находиться в GitHub Pages. **Secret key / service_role сюда не добавлять:** они обходят RLS.

## 4. Смена пароля без SMTP

Восстановление пароля через email пока отключено. Custom SMTP не требуется.

После входа кнопка **Change password** запрашивает текущий пароль, новый пароль и подтверждение. Минимальная длина в интерфейсе — 8 символов; требования Supabase могут быть строже. При создании аккаунтов через Dashboard используй Create new user с Auto Confirm вместо приглашений по email.

Если пользователь забыл пароль, потребуется административный сброс средствами Supabase; самостоятельно восстановить пароль в приложении пока нельзя.

## 5. Проверка перед публикацией

Запусти в каталоге проекта:

```bash
python3 -m http.server 8000
```

Открой `http://localhost:8000/`. Войди в созданный аккаунт.

- Добавь задачу и идею; проверь строки в Table Editor.
- Войди в тот же аккаунт на другом устройстве или в другом профиле браузера: изменения должны появляться без перезагрузки.
- Отключи сеть, измени задачу, перезагрузи приложение, затем включи сеть. Очередь должна отправиться автоматически.
- Измени одну задачу на двух отключённых устройствах: после подключения должен появиться выбор версии.
- Удали задачу на одном устройстве и измени её на другом офлайн: восстановление локальной версии создаёт новую запись.
- Войди во второй аккаунт: данные первого не должны отображаться.
- Проверь смену пароля и выход.
- При первом входе нажми **Import local data**, если есть старая локальная доска. Данные добавляются к аккаунту, оригинальные ключи остаются в браузере.
- Проверь Export / Import: импорт заменяет текущую доску и синхронизируется одной транзакцией.

После проверки опубликуй изменения обычным способом через GitHub Pages. Проверку входа и смены пароля повтори на production URL.

## Поведение и ограничения

- Офлайн работает после первого успешного открытия приложения и входа на устройстве. SDK лежит в проекте и кешируется service worker.
- Каждое действие сохраняется в localStorage вместе с очередью. Отправка идёт при изменениях, восстановлении сети, возвращении в приложение и каждые 30 секунд для повторов после временных ошибок.
- Realtime обновляет интерфейс сразу после записи в БД. После переподключения выполняется полная сверка.
- В одном браузерном профиле разрешена одна активная вкладка TaskFlow, чтобы вкладки не перезаписывали общую очередь. Другие устройства и профили работают одновременно. Нужен браузер с Web Locks.
- При выходе с пустой очередью изменений кеш данных очищается; если очистка подтверждений не завершена, её ID остаются локально. При выходе с ожидающими изменениями пользователь подтверждает сохранение очереди на устройстве; отправка продолжится после входа в тот же аккаунт.
- Конфликт предлагает сохранить локальный или серверный вариант. Выбор серверного варианта отменяет последующие локальные изменения конфликтующих записей. Остальные записи остаются в очереди.
- Синхронизация работает, пока приложение открыто; ОС может приостановить фоновую вкладку/PWA. После возврата выполняется сверка.
- Браузер может удалить данные сайта; Export остаётся способом резервного копирования.
